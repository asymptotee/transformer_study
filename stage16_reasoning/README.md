# stage16_reasoning —— 模型不是不会推理,是从来没人要求它推理

**判别式问题**:前面每个 stage 都撞在同一堵墙上 —— 模型只会**检索**,不会
**处理输入**。`12 × 8 = 40` 不是算错,是在检索一个看起来合理的数。
本阶段问:**这是能力天花板,还是数据问题?**

**答案:是数据问题,而且便宜得离谱。同一个 126M,14 分钟的"答案查不到"的
数据,把 5 位数加法从 0% 做到 83.5%。**

**顺带量出第二件事**:**分词把数字切成乱块,单独扣掉 26 个百分点**
(5 位数上扣 51 点)。

**但"便宜"这个说法后来要收窄(⑦节)。** 那 83.5% 绑死在一种句式上 ——
**换一个 `+` 就归零**。把句式铺到 30 种,未见句式才到 **78.6%**;
而只给 6 种句式、就算把步数翻三倍,也还是 **11.5%**。
**骨架多样性是主因,训练量替代不了它** —— 数据能造,但语料得真的铺宽。

## 设计

### 为什么必须是合成数据

自然文本里的答案**都查得到**,所以只能教检索。要逼它*处理*,训练分布必须满足:

> **答案在语料里查不到。**

程序化生成的算术天然满足:**每条输入的组合都是新的**。

### 格式:逐位加空格(这是个关键设计)

我们的 BPE 把连续数字切成和"位"不对齐的乱块:

```
1234  → ['12','3','4']                   67890 → ['6','7','8','90']
1 2 3 4 → 每数字 1 token ✅               单个 0-9 本来就各占 1 token
```

而多位数加法要求**从右往左按位对齐做进位**。token 边界和位边界不重合,
等于人为加难度。加空格后边界对齐,**且不用重训分词器**。

### 两组对照

| 组 | 格式 | 例 |
|---|---|---|
| **A 对齐** | 逐位加空格 | `1 2 3 4 + 5 6 7 8 = 6 9 1 2` |
| **B 对照** | 现有乱切 | `1234 + 5678 = 6912` |

两组**同题、同模型、同超参**,只差格式 —— 所以差值就是分词对齐的价值。

### 配置

起点 `ckpt_11_5_final.pt`(基座)· **继续预训练**(整行算 loss,不是 SFT)
· 窗口 **256**(基座原生;算术序列很短,5 位题约 30 token,不用外推)
· 5,000 步(300,000 条 ÷ batch 16 = 18,750 步/epoch,所以只跑了 **0.27 epoch**)
· **实测 14 分钟/组**

判据:**贪心生成,逐位精确比较**。不靠 judge —— 这是本阶段最大的优势,
前五个 stage 的度量都说反过话,这里不会。

## 结果

### 起点(基座,无任何算术数据)

| 位数 | 完全正确 | 长度对 |
|---|---|---|
| 1 | **21/200 = 10.5%** | 51/200 |
| 2 | **0/200** | 26/200 |
| 3 | 0/200 | 7/200 |
| 4 | 0/200 | 3/200 |
| 5 | 0/200 | 1/200 |

1 位数有 10.5%(不是零),2 位以上全零。**"长度对"的衰减(51→26→7→3→1)
说明它隐约知道答案该多长,但算不出来。**

### 两条曲线

| 位数 | **A 对齐** | **B 乱切** | 差 |
|---|---|---|---|
| 1 | **200/200 = 100%** | **200/200 = 100%** | **0** |
| 2 | **200/200 = 100%** | 177/200 = 88.5% | −11.5 |
| 3 | **183/200 = 91.5%** | 130/200 = 65.0% | −26.5 |
| 4 | **176/200 = 88.0%** | 88/200 = 44.0% | −44 |
| 5 | **167/200 = 83.5%** | 65/200 = 32.5% | **−51** |
| **合计** | **926/1000 = 92.6%** | **660/1000 = 66.0%** | **−26.6** |

test loss:A **0.8153** / B **1.3319**

## 结论

### ① 容量不是瓶颈 —— 数据是

| | 5 位数正确率 |
|---|---|
| 基座(无算术数据) | **0%** |
| + 14 分钟对齐数据 | **83.5%** |

**同一个 126M。** 所以"模型太小、要加深到 300-500M"这个判断**是错的,
正式撤回**。模型一直没有"不会算"的问题,它一直只被给过"答案能查到"的数据。

### ② 错误的形状说明它学的是算法

```
2 2 0 + 7 6 1 = → 期望 981   实得 962
2 5 2 + 8 6 3 = → 期望 1115  实得 1015
```

**全是"差一点"** —— 它在做逐位加法,只是**进位出错**。这是"算法学到但没学精",
不是能力天花板。而只训了 **0.27 epoch**,训久几乎必然更好。

### ③ 分词对齐值 26 个百分点,而且差距随位数单调放大

```
1位: 无差      ← 对齐在 1 位数上没有意义
2位: −11.5
3位: −26.5
4位: −44
5位: −51      ← 数字越长,乱切的代价越大
```

**这正是"token 边界与位边界错位"应有的形态。**

**而且两组的"长度对"都 ≈99%**(A 994/1000,B 991/1000)—— B 也知道答案该几位,
**只是算不出来**。所以分词影响的是**进位计算**,不是格式知识。

### ④ 这解释了 `12 × 8 = 40`

之前归为"有外壳没内核",像是能力问题。**实际是两件事叠加**:

1. **从没有过"答案查不到"的训练数据** → 它只会检索
2. **分词把数字切成乱块** → 即使想算,进位也无从对齐

**两条都是工程问题,不是能力天花板。**

### ⑤ 但那 92.6% **完全是格式绑定的**(2026-09-23 补测)

上面四条结论都建立在"92.6%"这个数上。**补了泛化测试之后,它要加一个限定。**

**设计**:同一批算式,换 **5 种措辞**,答案内容不变。A 是同款作对照。

| 措辞 | 正确率 |
|---|---|
| **A 训练同款** `1 2 3 4 + 5 6 7 8 =` | **738/800 = 92.3%** |
| B 汉字算符 `1 2 3 4 加 5 6 7 8 =` | **0/800 = 0%** |
| C 问句 `计算 … 加 … 等于多少？` | **0/800 = 0%** |
| D 自然写法 `1234 + 5678 =`(不逐位空格) | **5/800 = 0.6%** |
| E 三加数 `1 2 + 3 4 + 5 6 =` | **0/800 = 0%** |

**换掉 `+` 这一个符号,加法能力就没了。**

**但要同时说清另一面:它确实在算。** A 组是**全新随机数字**上的 92.3%,靠背背不出来 ——
那个计算回路是真的。**问题不在"会不会算",在"接口"**:能力被绑死在
`d + d =` 这个**字面 token 模式**上,模式一变,回路不触发。

**准确说法:它学会了「在这个格式下执行加法」。**

### ⑥ 格式混合:迁移成立,但半径有限

那**把多种格式混着训**会怎样?训练集 = 5 种格式各 12,000 条等量混合。

**训练时见过的 5 种:**

| 格式 | 正确率 |
|---|---|
| S1 `… + … =` | 684/800 = **85.5%** |
| S2 `… 加 … =` | 696/800 = **87.0%** |
| S3 `计算 … 加 … 等于多少？` | 726/800 = **90.8%** |
| S4 `1234 + 5678 =` | 422/800 = **52.8%** |
| S5 `1 2 + 3 4 + 5 6 =` | 114/800 = **14.3%** |

**训练时没见过的 4 种 ★:**

| 格式 | 正确率 | |
|---|---|---|
| **U1 `… 加上 … 等于几？`** | **674/800 = 84.3%** | ✅ 新词组合,迁移成功 |
| **U4 `1234 加 5678 =`**(两处变化叠加) | **397/800 = 49.6%** | ✅ 也迁移了 |
| U2 `求 … 与 … 的和。` | 29/800 = 3.6% | ❌ 句式结构变了 |
| U3 `计算：… + …`(无等号) | **0/800 = 0%** | ❌ 靠 `=` 定位答在哪开始 |

**三条读数:**

1. **迁移是真的**:`加上…等于几？` 训练时一次没见过,拿到 **84.3%**。
   对比单格式训练(换一个 `+` 就归零)—— **格式多样性确实撑开了泛化半径**
2. **但边界在「语句结构」上**:换词能过,句子骨架变了过不去;
   **U3 无等号 = 0%** 尤其说明它靠 `=` 当"该开始答了"的信号
3. **混合有代价,而且可量化**:
   ```
   S1 单格式训:   92.3%        ← 换一个词 → 0%
   S1 五格式混训: 85.5%(−6.8)  ← U1 从 0% → 84.3%(+84)
   ```
   **用 7 个点的专用性换 84 个点的通用性。** 另外 S5(三加数)只 14% ——
   混合并不能让每个格式都学好。

### ⑦ 骨架多样性是主因,而且**训练量替代不了它**(2026-09-28/29)

**为什么做**:⑥ 只给了曲线上的**一个点**(6 种骨架 → 未见骨架 1–7%)。一个点不能回答
"语料里到底要放多少种骨架" —— 而这个数直接决定从零方案的语料制备成本:

| 若 K 小 | 若 K 很大 |
|---|---|
| 手写骨架就够,**不用起 LLM 批量生成** | 手写不可行,**LLM 生成才是必须的** |

**设计**(`gen_arith_bank.py`):骨架库 `BANK` **有序**,N 取前缀 ——
`BANK[0:6]` **逐字等于** ⑥ 那 6 种,`HELD`(10 个)永远不训。所以 N=6/15/30
三次训练是**嵌套**的,唯一变量就是骨架数。每骨架固定 1 万条。

#### 第一轮:5000 步

| 训练骨架数 | ★ 未见 10 个 | 见过的 |
|---|---|---|
| **N=6** | 309/4000 = **7.7%** | 348/2400 = 14.5% |
| **N=15** | 1339/4000 = **33.5%** | 3276/6000 = 54.6% |
| **N=30** | 1819/4000 = **45.5%** | 6362/12000 = 53.0% |

**7.7 → 33.5 → 45.5。** 但这条曲线同时动着**两个量**:数据量随 N 涨
(6万/15万/30万),而步数固定 5000 —— 所以 **N 越大,每个骨架被重复的次数越少**。
**"骨架数"和"总训练量"在这里是缠在一起的,分不开。**

而且 N=30 的"见过的"只有 53.0% —— 一批训过的格式还很弱(`T18带标签 7.8%`、
`T13求和冒号 11.2%`、`T21逆序操作 15.2%`)。**训练本身就没做完。**

#### 第二轮:把步数抬到 15000(数据、骨架一字未改)

这是本节的**判决性实验**。同一套骨架库,只动步数:

| run | 骨架数 | 步数 | ★ 未见 | 见过的 |
|---|---|---|---|---|
| n6 | 6 | 5000 | 7.7% | 14.5% |
| **n6x3** | **6** | **15000** | **11.5%** | 18.1% |
| n30 | 30 | 5000 | 45.5% | 53.0% |
| **n30x3** | **30** | **15000** | **78.6%** | 83.8% |

**同样三倍步数:6 个骨架只买到 +3.8 点,30 个骨架买到 +33.1 点。**

#### 判决:同一批 6 个骨架,同一批步数

那 6 个骨架**五个 run 都训过**。所以可以拿它们做最干净的一个对照 ——
**同一批骨架、同样 15000 步,唯一差别是训练时旁边有没有别的 24 种骨架**:

| 共享骨架 | n6x3(只有这 6 个) | n30x3(另有 24 个) |
|---|---|---|
| **T01纯符号** | **1.0%** | **61.5%** |
| T02无等号 | 53.2% | 96.8% |
| T03求和 | 47.0% | 95.5% |
| **T04疑问** | **3.2%** | **95.5%** |
| T05自然写法 | 2.0% | 49.2% |
| T06应用题 | 2.0% | 75.8% |
| **合计** | **434/2400 = 18.1%** | **1897/2400 = 79.0%** |

**它学不会自己那 6 个骨架,除非旁边站着别的骨架。**

**这不是"多训",是"多训别的" —— 别的骨架的存在,是它学会这 6 个的前提条件。**

#### 顺带排掉的:过拟合,和"必须有结构近亲"

**不是过拟合。** n6x3 跑了 4 epoch(6万条 × 15000 步),但 test 0.8645 < train 0.9014。
而且过拟合会**抬高**见过的准确率,它只从 14.5% 抬到 18.1%。

**不是"必须有结构近亲"**。拿每个未见骨架和训练库里最像的那个算形状相似度
(`bank_similarity.py`),和准确率相关:

```
r = 0.315(弱)
H03祈使   相似度 0.286 → 79.5%   ← 低相似度、高准确率
H09往后数  相似度 0.158 → 71.2%   ← 最低之一,却过了七成
H07编号列表 相似度 0.182 →  0.0%   ← 同档相似度,却是零
```

**H03、H09 在训练库里没有近亲,照样过 70%** —— 所以真有"多样性红利"这回事,
不是撞近亲。H09 尤其值得记:它是**换一种描述方式**(`从 X 开始往后数 Y 个`),
n30x3 拿到 **95.8%**。

#### 那个 0% 是个数字问题,不是能力问题

H07 是唯一三次都不动的。同一个 N=30 模型,同一批数:

| H07 的三种写法 | 正确率 |
|---|---|
| `1) X` / `2) Y` / `合计：`(原样) | **0.0%** |
| `a) X` / `b) Y` / `合计：`(序号换字母) | **31.2%** |
| `X` / `Y` / `合计：`(去掉序号) | **60.5%** |

**训练库 30 种骨架里,提示中出现的每一个数字都是操作数。** 于是它学成了
**"提示里的数字 = 要算的数"**,`1)` `2)` 也被当成操作数。

**而加三倍步数也救不回来** —— n30x3 上它从 0% 只爬到 4.5%,同期其余九个在
62–97%。**这个偏置是训练分布刻进去的,不是训练量能磨掉的**,只有改分布能解决。

> **语料设计的第一原则要扩写:不只是"多种句式",还必须让「非操作数的数字」出现在
> 提示里** —— 序号、单位、年份、数量词。否则模型学到的规则是"提示中所有数字相加",
> 而不是"找到被要求的那两个数"。

#### 意外收获:loss 在这里**不测量泛化**(第 7 个被识破的指标)

| run | 最终 test loss | ★ 未见迁移 |
|---|---|---|
| n6x3 | **0.8645** | 11.5% |
| n30x3 | 0.8987 | **78.6%** |

**n6x3 的 loss 反而更低,迁移率差 7 倍。** 两个模型收敛到几乎相同的 loss,
泛化能力天差地别 —— 和前面六次一样,**汇总数字看着能用,实际会骗人**。

#### 对从零方案的回答

> **骨架多样性不是可选项,也没法用训练量换。**

6 种不够(三倍步数也只到 11.5%),30 种很够(78.6%)。所以"手写少量模板 +
训久一点"这条便宜路**两头都堵死了** —— **语料必须真的铺结构多样性**,
这反过来给 LLM 生成语料提供了正当性。

**还没回答的**:饱和点在 6 和 30 之间的哪里(N=15@15000 没跑)。

### ⑧ Holmes v1 实测:参照实现没有兑现承诺

**为什么测**:Holmes 就是我们讨论的"专注推理、原生思维链、舍弃知识"那条路的
参照实现。**它的效果直接决定这条路值不值得走。** 而它没有公开的 benchmark 数字
(知乎专栏要登录、HF 被墙),只能自己跑。

**模型**:`ej2/Holmes_history` 的 `150b_token_instruct`(v1 稠密 0.5B,548M 参数,
词表 64,003,**40 层 × 1024 维** —— 又深又窄,是为推理做的架构选择)。

**算术 n=60(两种问法各一遍,结果一致):**

| 位数 | 答对 |
|---|---|
| 1 位 | 3/20 |
| 2 位 | 0/20 |
| 3 位 | 0/20 |
| **合计** | **3/60 = 5%** |

```
计算 4 + 3 → 4 + 3 = 8  所以，4 + 3 = 8  答案是8。   ❌ 应 7
计算 1 + 8 → 1 + 8 = 16  所以，1 加 8 等于 16。      ❌ 应 9
```

**其他维度(n=20):**

| 类别 | 得分 | 典型失败 |
|---|---|---|
| 形式逻辑 | **2/6** | 把"这个推理有效吗"理解成"这个事实对不对" —— **在讨论物理,不在讨论逻辑** |
| 关系推理 | **0/3** | 连"谁最矮"都答不出,复读题面 |
| 状态追踪 | **1/3** | `5-2+7` 算成 `5+2+7=15`(符号看错) |
| 指令变换 | **2/4** | 加"吗"、加"不"能做;**倒序、删字完全不会** |
| 代码 | **0/2** | `len([1,2,3])` → "123456789";`2**3` → 12 |
| 中文理解 | **0/2** | 数水果数错 |
| **合计** | **7/20** | |

**它的失败模式和我们 126M 同源**:格式像样(分点、"因此"、"所以"齐全)、
内容靠检索、**然后陷入无限复读**。

**一个必须说的观察:每一题的开头都"像在推理"。** 不实测的话,看输出会以为它在思考 ——
**这正是"格式完整但内容靠检索"最难识别的地方**,也是本项目六次被代理指标骗过的同一件事。

**⚠️ Caveats**:测的是 v1 稠密(`150b_token_instruct`),**v2 MoE 没测**(README 说 v2 更新);
打了 2 处 API 兼容补丁(**不改语义**,见坑 7);贪心解码;每类 2–6 题,
**不是统计意义上的评测**。另外**我们自己的 126M 没测过这些题** ——
"Holmes 不行"不等于"我们的行"(不过已知基座逻辑探针 1/8)。

## 这一步在项目里的位置

前五个 stage 全被同一件事卡住:**语料有限 + 判分靠代理**。而这个任务:

| | |
|---|---|
| **数据能无限造** | 程序生成,难度分布可精确控制 |
| **判分不会骗人** | 逐位精确比较,没有 judge 可被误导 |
| **难度曲线能画出来** | 位数就是难度旋钮 |
| **顺便补上 RL 那段** | 奖励 = 答案对不对 → **可验证奖励** |

**这是本项目第一个"数据能造、答案能验"的任务。** README 里一直挂着的
RL 那一段,在这里才有干净的落地条件。

## 下一步(2026-09-29 更新)

**⚠️ 下面第 3–4 条在新结果之后都要打折** —— 92.6% 是**格式绑定**的(⑤节),
而格式混合只把泛化半径撑到 84%,**过不了语句结构的变化**(⑥节)。

**⑦节把这条线推到了"要多少种骨架"上,答案变了两次,最终是:
骨架多样性是主因,训练量替代不了它。**

**现在最该做的是**:

1. **★ 饱和点在 6 和 30 之间** —— ⑦节只测了两个端点(n6x3 11.5%、n30x3 78.6%)。
   跑 **N=15 @15000 步**就能知道曲线是"陡升后平"还是"线性"。
   **这个数决定语料要铺多宽**,是目前最省的一个未知数(~40 分钟)
2. **语料第一原则(⑦节扩写)**:除了多种句式,**还必须让「非操作数的数字」进入提示**
   —— 序号、单位、年份、数量词。否则学到的是"提示中所有数字相加"而不是
   "找到被要求的那两个数"。H07 就是这个偏置的活标本
   —— 而且 **n30x3 证明加三倍步数也救不回来**(0% → 4.5%),必须靠改分布
3. **句式多样性要更激进** —— 不只是换词,要换**句式骨架、标点、语序、有无 `=`**。
   ⑥节显示 U3(无等号)是 0%,说明模型用 `=` 当"该开始答了"的开关
4. **乘法和多步表达式** —— 但要**一开始就多种句式**,否则又是一轮格式绑定
5. **RL(可验证奖励)** —— 条件仍然齐全(答案可程序验证 + 数据可无限造)

**保留的结论**:
6. **如果要开新模型**:分词器改成**数字逐位**(比逐位加空格省 token),
   并在预训练语料里混入合成推理数据 —— 否则它永远学不会"处理"

**已作废的旧结论**:~~"训久一点"~~(会学到更牢的格式绑定,不是更通用的能力)、
~~"长度泛化"~~(在格式绑定没解决前测不出真东西)

## 踩过的坑

1. **监视器"死了"是误判**:我用 `ps | grep "seq 1 200"` 判断后台监视器是否存活,
   匹配方式不对就以为它死了,还重挂了一个。**实际它一直正常**
   (`bfrdpf5i1` 后来正常返回了完整结果)。**教训:判断后台任务存活要用它自己的
   机制,别靠 ps 猜**
2. **起飞前检查显存** —— 这次照做了(stage15 那次因为没查,把整机拖死过)。
   见 `stage15_toolcall/README.md` 的运维事故一节
3. **判据两侧不对称,把"全对"记成 0/800**(第 6 个被识破的度量)。
   `eval_arith.py` 的判据是 `re.sub(r"\s+","",模型输出) == r["a"]` ——
   **它只归一化模型输出那一侧**。而 `gen_arith_mixed.py` 第一版把答案写成
   逐位空格的 `d(a+b)`,于是 `59+84=143` 这种全对的答案被判 0/800,
   **五个训练格式全部"归零"** —— 看起来像"混合训练把能力毁了",
   实际是判据问题。**线索**:test loss 0.93 的模型不可能全错
   (和 stage15 的 `msgs[:2]` 那次一样 —— **两个数放在一起说不通时,先怀疑测量**)
4. **SSH heredoc 里的修补脚本静默没跑**。第一次修上面的 bug 时,我把 python
   修补脚本用 `ssh '... <<"EOF" ... EOF'` 传过去,**它没有任何输出,我误以为它跑成功了**,
   于是重跑评测得到同样的 0/800,白跑一轮。**改成把脚本写成文件再 rsync 过去**,
   立刻看到"修好 9 个文件"。**教训:远程执行的脚本要能自证跑过了**(打印结果),
   不能只看"没报错"
5. **"见过的骨架"这个对照差点用错**(⑦节)。第一版的汇总表里"N=15 的见过 54.6%
   比 N=6 的 14.5% 高",看起来像**训练更充分**;实际是因为 `BANK[6:15]` 那 9 个
   恰好更好学。**汇总平均会把"骨架难度差异"读成"训练量差异"。**
   真正的对照是**三次都训过的那 6 个**(T01–T06 跨 run 比)。
   **教训:对照要"同一批样本跨条件比",不是"每个条件下各自平均"**
6. **一个跨三次实验都不动的 0%,值得单独查**(H07)。它三次都是 0.0%,而其余 9 个
   都在涨。查下去发现不是判据、不是能力,是**提示里的序号数字**被当成操作数 ——
   换字母序号立刻 31.2%。**教训:极端的离群值优先怀疑"输入格式",而不是"能力"**
   (⑤⑥两节也栽在同类事上:换一个 `+` 归零、无等号归零 —— 都是**接口**不是**能力**)
7. **loss 不测量泛化**(第 7 个被识破的指标)。n6x3 的 test loss 是 **0.8645**,
   n30x3 是 **0.8987** —— loss 更低的那个,**未见骨架迁移率差 7 倍**(11.5% vs 78.6%)。
   两个模型收敛到几乎相同的 loss,泛化能力天差地别。
   **教训:这个项目的每个阶段都要有一个"不靠 loss、不靠 judge"的判据** ——
   本阶段能有结论,靠的是**逐位精确比较 + 未见骨架**这套组合
8. **Holmes 在 Spark 上跑不起来的两处 API 不兼容**(transformers 4→5):
   - `rope_scaling: null` 被 5.x 规范化成字典 → 他们的 `["type"]` 报 KeyError
   - `DynamicCache.get_max_length()` 已被移除(5.x 里叫 `get_max_cache_shape`)
   **两处都做了兼容补丁,不改语义**(rope 分支判定 + cache 长度查询)。
   **跑法**:装隔离的 `transformers==4.50.1` 到 `--target` 目录,用 `PYTHONPATH` 屏蔽**
   ```bash
   pip install --target ~/llm_study/tf450 "transformers==4.50.1"

   ```
